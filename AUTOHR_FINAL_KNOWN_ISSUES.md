# KONE AutoHR — Final Known Issues & Operational Constraints

**Release Candidate:** v0.1-RC  
**Target Environment:** Windows 10 / Windows 11 Enterprise  
**Applies to:** KONE AutoHR Web Application (Pre-Desktop Migration)

---

## 1. Hardware & System Audio Dependencies

### 1.1 VB-Audio Virtual Cable Requirement (QA-010)
- **Description:** For Microsoft Teams meeting participants to hear AI speech synthesis (Sarvam TTS) or audio playback generated by the AutoHR bot, audio must be piped from AutoHR's playback device into Microsoft Teams' microphone input.
- **Dependency:** [VB-Audio Virtual Cable](https://vb-audio.com/Cable/) (or equivalent virtual audio driver) must be installed on the host machine.
- **Routing Setup:**
  - AutoHR Playback Device ➔ `CABLE Input (VB-Audio Virtual Cable)`
  - Microsoft Teams Microphone Device ➔ `CABLE Output (VB-Audio Virtual Cable)`
- **Software Diagnostic vs Physical Verification:**
  - AutoHR includes a built-in Virtual Audio Bridge diagnostic card on the Session page (`/sessions/$id`) with `GET /runtime/audio/devices` and `POST /runtime/audio/test-playback`.
  - HR can click **"Test Audio Bridge Chime"** to transmit a 440 Hz test tone directly through the virtual cable to verify Microsoft Teams microphone level deflections.
  - *Distinction:* API verification confirms driver binding and audio packet dispatch. Physical verification requires an active meeting where remote human listeners confirm clear reception.

### 1.2 Windows System Volume & Device Exclusivity
- **Constraint:** Windows Audio Exclusive Mode (WASAPI Exclusive) can occasionally block the virtual cable if another communication application acquires exclusive control.
- **Recommendation:** In Windows Sound Control Panel (`mmsys.cpl` ➔ Advanced tab for both CABLE Input and CABLE Output), ensure *"Allow applications to take exclusive control of this device"* is disabled.

## 2. Microsoft Teams & Playwright Automation Constraints

### 2.1 Persistent Microsoft Edge Profile Authentication
- **Description:** Enterprise Microsoft Teams tenants enforce conditional access, corporate SSO, or Multi-Factor Authentication (MFA). Headless anonymous joins are often blocked by corporate security policies.
- **Operational Requirement:**
  - AutoHR uses a persistent Microsoft Edge user data directory (`backend/app/services/meeting_bot_service.py`).
  - An HR administrator must open Microsoft Edge once under the designated profile and log in to the corporate Teams account before running automated bot sessions.
- **Mitigation:**
  - If the bot encounters an expired session or unexpected MFA challenge, it halts gracefully and emits an authentication-required status rather than crashing.

### 2.2 Teams Lobby Admission
- **Constraint:** Depending on the meeting organizer's lobby policy (*"Who can bypass the lobby"*), the AutoHR bot may be held in the virtual lobby until an organizer or presenter clicks "Admit".
- **Mitigation:**
  - The AutoHR Meeting Status card explicitly displays `State: IN_LOBBY` with a guidance tip: *"Bot is waiting in the Microsoft Teams lobby. Please admit the bot to proceed."*
  - The "Start Induction" button safely disables while in the lobby and enables as soon as admission is confirmed.

### 2.3 PowerPoint Screen Sharing Layout Variations (QA-011)
- **Constraint:** Microsoft Teams Web UI periodically receives interface updates from Microsoft (e.g., changes to presenter mode, PowerPoint Live, or screen sharing video container selectors).
- **Behavior:** The `PresentationObserver` relies on DOM selectors and OCR visual comparison to detect slide changes. If the meeting presenter shares via "PowerPoint Live" rather than full-screen window sharing, standard video stream extraction may not yield visual frames.
- **Mitigation / Workaround:**
  - Presenters should share the PowerPoint slideshow via **"Window"** or **"Screen"** mode for optimal automated tracking.
  - If automatic screen detection cannot lock onto the presentation, the "Start Induction" button allows a manual override with HR confirmation (QA-011).

## 3. Infrastructure & Environment Dependencies

### 3.1 PostgreSQL Database Requirement (QA-001)
- **Constraint:** The current web application backend requires an active PostgreSQL database instance specified in `.env` (`DATABASE_URL=postgresql+psycopg2://...`).
- **Software Diagnostic vs Physical Startup:**
  - `backend/main.py` catches connection errors and outputs a sanitized diagnostic message identifying the unreachable host without leaking credentials.
  - *Distinction:* Improved error reporting prevents silent crashes and masks secrets, but physical startup will halt with `[FATAL STARTUP ERROR]` until a real PostgreSQL instance is running and accessible on the network.
- **Future Resolution:** Desktop application conversion will replace PostgreSQL with a local SQLite database file, removing this external dependency.

### 3.2 Attendance Telemetry Collection vs Reporting (QA-007)
- **Constraint:** Live participant telemetry depends on Playwright inspecting the Microsoft Teams participant roster DOM during the call.
- **Behavior:** If the bot cannot access the roster DOM (e.g. tenant restrictions or custom Teams UI), no participant join/leave events will be logged.
- **Mitigation:** The reporting engine handles zero telemetry gracefully by marking attendance as `"Unverified (No participant signals captured)"` with 0% participation, strictly preventing synthetic 100% inflation.

### 3.3 Report Export Formats (QA-005)
- **Supported:** Formatted PDF (`.pdf`), Microsoft Word (`.docx`), and disk Markdown (`.md`).
- **Roadmap Pending:** Standalone `.csv` download route is not implemented. Roster details are contained in PDF and DOCX tables.
